# 我花了一下午让 Claude Code 遵循"规格驱动开发"，结果出乎意料

> 本文由 Claude Code 基于我与她的真实开发对话总结撰写，所有数据和引用均来自公开研究。

## 先说说为什么我要搞这个

最近在玩 Claude Code 写代码，体验大概是：简单需求一把梭，效果不错。但稍微复杂一点的功能，就开始出问题了——AI 写出来的代码方向偏了、边界情况没处理、聊了 20 轮之后它忘了最初在说什么。改一个地方崩三个地方，没有回归保护。

如果你也在用 AI 写代码，大概率也有同感。这事儿甚至有数据支撑：

**84% 的开发者在用 AI 编码工具，但只有 29% 信任它们。** GitClear 分析了 2.11 亿行代码，发现 AI 生成的代码重复率是手写的 4 倍。CodeRabbit 分析了 470 个真实 PR，发现 AI 生成的代码问题数量是手写的 1.7 倍——逻辑错误多了 75%，安全漏洞多了 1.5-2 倍，性能问题多了 8 倍。

最离谱的是：**96% 的开发者认为 AI 生成的代码不完全是正确的，但只有 48% 每次都检查。** 换句话说，一半人知道代码可能有 bug，但还是直接 commit 了。

Simon Willison 说得很到位："如果 LLM 写了代码，你 review 了、测试了、能给别人解释清楚了——那不叫 vibe coding，那叫软件工程。"

所以我开始琢磨：有没有什么办法能让 AI 写代码的过程更可控？

## Vibe Coding 的真实代价

"Vibe Coding" 是 Karpathy 在 2025 年初造的词，指的是用自然语言跟 AI 对话来写代码，而不是一行一行自己敲。听起来很美，但实际用起来，坑不少。

ICSE-SEIP'26 的一篇灰色文献综述调研了 114 个从业者的真实体验，发现：

- **68%** 的人认为 AI 生成的代码是"快但不靠谱"——速度上去了，但长期质量是问题
- **63%** 的人报告说花在调试 AI 代码上的时间比手写还多
- **11%** 的人直接放弃了项目——因为 AI 生成的代码太乱、bug 太多，修不下去

Red Hat 的一篇文章用了一个很精确的描述：**"vibe coded 项目通常在三个月左右撞墙。"** 因为代码库已经膨胀到没人能完全理解了，AI 的上下文窗口只能看到碎片，你手头没有一份可以回溯的地图。

METR 做过一个随机对照实验，让有经验的开源开发者分别用 AI 和不用 AI 完成复杂任务。结果？**用 AI 的反而慢了 19%。** 但 80% 的人还是更偏好用 AI，因为"感觉更轻松"。这大概就是"感觉快"和"实际快"的区别。

Faros AI 的遥测数据更扎心：10000+ 开发者、1255 个团队的统计显示，用了 AI 之后个人完成了 21% 更多任务、提交了 47% 更多 PR——但 PR review 时间增加了 91%，因为要审的代码多了 98%。个人效率上去了，团队整体速度被拖垮了。

所以问题不在于 AI 能不能写代码，而在于怎么让它写出的代码可控、可审查、可维护。

## 但话说回来，vibe coding 也不是一无是处

在猛踩 vibe coding 之前，得承认它在某些场景下确实很好用。

**快速原型。** 有时候你就是想验证一个想法能不能跑通，不关心代码质量、可维护性、架构优雅。Bolt.new、v0 这类工具让你 5 分钟出一个能看的 demo，这在以前是不可能的。RedMonk 分析师 Kate Holterhoff 说 2026 年 41% 的全球代码是 AI 生成的——这不可能全是在写生产级代码，绝大部分都是原型和实验。

**降低门槛。** Stack Overflow 上有个非技术背景的编辑写了一篇文章，讲她用 vibe coding 从零搭了一个项目。虽然她自己承认代码是"一团糟"，但她学会了编程的基本概念，而且这个项目确实能用。对于学习、实验、内部工具来说，vibe coding 的价值是真实的。

**资深开发者的效率加成。** Hashnode 的分析指出，10 年以上经验的开发者用 AI 工具能获得 81% 的效率提升。他们知道好代码长什么样，能一眼看出 AI 哪里写错了。问题主要出在经验不足的开发者身上——junior 用 AI 的效率提升只有 15-25%，因为他们缺乏判断力去评估 AI 的产出。

所以 vibe coding 真正的问题不是"能不能用"，而是"在什么场景下用"。用来验证想法、学习概念、搭内部工具，完全没问题。用来写生产代码、多人协作的项目、需要长期维护的系统，那就是在给自己埋雷。

## AI 编程的核心矛盾

聊到这里，其实可以抽象出一个更底层的问题。

AI 编程的本质是一个翻译过程：**把人的意图翻译成代码。** 翻译质量取决于两个因素——意图的精确度，以及 AI 的理解能力。前者你可控，后者你不完全可控。

这就引出了一个根本性的矛盾：

**意图越精确，前期成本越高；意图越模糊，后期修错成本越高。**

Vibe coding 和 SDD 可以看作是这个光谱上的两个极端：

```
意图精确度：  低 ◄─────────────────────► 高
前期成本：    低                              高
后期风险：    高                              低
认知负担：    低（你说几句话就行）             高（要写 spec、做决策）
反馈速度：    快（秒级看到结果）               慢（要走完流程才写代码）
```

Vibe coding 选了左边——低认知负担、快速反馈，但后期风险不可控。SDD 选了右边——高前期投入、慢反馈，但产出质量更可预期。

大多数讨论都在争论"该选哪边"，但真正的问题是：**有没有办法根据具体场景动态地在这条光谱上选择位置？**

这就是为什么我觉得 Martin Fowler 的批评特别有价值——他不反对 SDD，他反对的是"所有场景都走完整流程"的一刀切。SDD 的 spec 有轻重之分，一个 5 行的 spec 和一个 50 行的 spec，提供的是不同级别的精确度，对应的前期成本也完全不同。

理解了这个矛盾，后面讨论 SDD 的优缺点和适用场景就有了统一的框架。

## SDD：一个不那么新的"新"方案

SDD（Spec-Driven Development）的核心思想极其简单：**先写清楚"要做什么"，再让 AI 去做。**

这不是什么新概念。瀑布时代写需求文档，敏捷时代写 User Story，本质上都在干这件事。但 SDD 在 AI 编程时代有了新的意义——因为 AI 编码助手跟人不一样，它不会"猜"你的意图，或者说它猜得不好。

GitHub 的说法是："在 AI 时代，维护软件意味着维护规格。开发的通用语言向更高层次迁移，代码成了最后一公里。"

MSR'26 收录了一篇 SDD 的学术论文（ACM AIWare 2026），把 SDD 分成了三个层次：

1. **Spec-First**——先写 spec，然后用它指导 AI 生成代码。最轻量，适合单个功能的开发。
2. **Spec-Anchored**——spec 在任务完成后保留，作为后续维护和演进的基准。中等投入，适合需要长期维护的功能。
3. **Spec-As-Source**——spec 是唯一的主文件，人类只编辑 spec，代码完全由 AI 生成。最重，适合 spec 相对稳定、技术栈可能变化的场景。

这三个层次其实就是在前面的光谱上选择了三个不同的"停靠点"。Spec-First 是最靠近 vibe coding 的——你只花几分钟写个简要 spec，就能显著提升 AI 的输出质量。Spec-As-Source 是最远的——你需要持续维护 spec，但换来了"代码可以随时丢弃重建"的能力。

Martin Fowler 在他深入体验了 Kiro、Spec-kit、Tessl 三个 SDD 工具之后写了一篇文章，态度挺克制的。他指出了一些真实问题：

- **"虚假的控制感"**——即使有了完整的 spec 和模板和 checklist，AI 还是经常不按规矩来。上下文窗口大了不代表 AI 会认真读里面的每一条。
- **markdown 爆炸**——Spec-kit 给他生成了大量冗余的 markdown 文件，又长又重复，"说实话，我宁愿 review 代码也不想 review 这些 markdown。"
- **过度设计**——修一个小 bug 也要走完整的 spec → plan → tasks 流程，杀鸡用牛刀。

Fowler 的结论是：SDD 工具需要更好地支持迭代式开发，小的、原子化的工作包，而不是上来就搞一堆前置设计。这个观点我觉得很对——本质上他是在说，我们需要在光谱上自由移动，而不是被锁在某个极端。

## 社区里的人是怎么玩的

调研了一圈，发现已经有一批人在实践 SDD 了，而且玩得挺花。

一个叫 Ivo Kund 的开发者做了一个相当硬核的实验：**把自己的项目的 src 目录全删了，然后只靠 spec 重新生成。** 他用 Claude Code 跑了大约 1 小时，花了 1% 的周配额。Claude 停在了 94% 测试覆盖率，报告说"挺好的"，他不得不打断一次说"你还没完呢"，然后很快就全部通过了。

最后 Claude 还自动把原始版本和重建版本在浏览器里并排打开，截图、对比、分析差异。Ivo 说结果就像"跳到了一个平行宇宙，同样的东西但有一点点不同"——那些微小的差异正好暴露了 spec 里没写清楚的地方。

这个实验很能说明问题：spec 的质量直接决定了重建的质量。那些"一点点不同"不是 AI 的问题，是 spec 没覆盖到的角落。如果你能做到 spec 足够完整，Spec-As-Source 是可行的。但现实中，spec 的完整性本身就是一个很难保证的事情。

他的工作流里还有个很有意思的细节：他会启动一个 peer review 子代理，这个子代理会调用 Gemini CLI 和 Amazon Q Developer CLI 来审阅需求文档。没错，用三个不同的 AI 来互相 review。他觉得不同模型的系统 prompt 和参数设置确实能提供不同视角。

另一个案例来自 XB Software 团队。他们用 GitHub Spec-kit 做了实验，发现了一个关键规律：**spec 的大小必须匹配任务的大小。** 试图一次性生成整个应用，模型会崩溃，产出不可用。把项目拆成小的、边界清晰的功能点，每个单独出 spec，质量就稳定了很多。

这个发现和前面提到的核心矛盾完全吻合——意图的精确度要匹配任务的复杂度。小任务写大 spec 是浪费，大任务写小 spec 是摆设。

还有人把 spec 和 BDD 框架结合起来。Ivo 用了 ThoughtWorks 的 Gauge——一个用 Markdown 写 spec 的 BDD 框架，配合 Playwright 做 e2e 测试。75 个 e2e 测试 23 秒跑完，甚至可以作为 pre-commit hook。这样 spec 就不仅仅是文档了，它是真正可执行的验证。

Artur Less 在 Level Up Coding 上写了一篇很实在的文章："如果你用过 AI 编码代理做真实项目，你会发现一个不舒服的事实：产出质量极其不稳定。同一个工具、同一个模型，一次产出干净架构良好的代码，下一次就是一团乱麻，修的时间比重写还长。问题不在 AI，在于流程——或者说，缺乏流程。"

## SDD 的三个真实取舍

写到这里好像 SDD 完美无缺似的。实际上它面临的不是"缺点"，而是**结构性的取舍**——你得到一些东西，就必须放弃另一些东西。

### 取舍一：精度 vs 灵活性

spec 写多细？这是 SDD 最核心的张力。

写得太细，你其实是在做瀑布时代做的事——需求还没开始写代码就锁死了。一旦需求变了（而需求几乎一定会变），你要同时改 spec 和代码，维护两份"真相"。敏捷运动当年就是因为这个才抛弃了重型前置设计的。

写得太粗，AI 又回到了"猜"的模式，SDD 的价值大打折扣。一个只写了"实现用户登录"的 spec，和直接跟 AI 说"帮我写个登录功能"，没有本质区别。

InfoQ 的一篇文章指出了这个问题的本质：SDD 没有消除复杂性，只是把复杂性从代码转移到了 spec 上。spec 变成了一种"长期可执行的基础设施"，会积累技术债务、跨团队耦合、兼容性惯性——这些原本是代码才有的毛病。

所以真正的难点不是"要不要写 spec"，而是**spec 应该写到什么粒度**。这个粒度取决于需求变化的概率——变化快的功能，spec 保持轻量；变化慢的核心逻辑，spec 可以写详细些。一刀切是行不通的。

### 取舍二：前置投资 vs 回报的不确定性

SDD 要求你在写代码之前投入时间写 spec、做 plan、拆 task。这个投资能不能收回来，取决于你一开始对需求的理解有多准确。

如果你对需求理解得很清楚，SDD 的前置投资回报很高——AI 生成的代码质量显著提升，后期的调试和返工成本大幅降低。

如果你对需求理解得不够清楚（而这种不确定性在软件开发中非常常见），你可能花了 30 分钟写了一份 spec，写到一半发现需求本身就定义错了。这时候 spec 不是在帮你，而是在浪费你的时间。而 vibe coding 在这种情况下反而有优势——你可以先写个粗糙的版本跑起来，再根据实际运行效果调整需求。

换句话说：**SDD 假设你能事先把需求想清楚。但很多时候，你不写代码就根本不知道需求是什么。** 这不是 SDD 的 bug，这是软件工程的本质困难。

### 取舍三：审查对象的转移

SDD 把审查的重点从代码转移到了 spec。听起来很合理——审一个 50 行的 spec 比审 500 行代码容易多了。但 Martin Fowler 的体验说明这不一定成立。

Spec-kit 生成了大量 markdown 文件，又长又重复。Fowler 说"我宁愿 review 代码也不想 review 这些 markdown"。为什么？因为这些 spec 文件本身也需要理解和判断——它们可能包含模糊的描述、遗漏的边界条件、自相矛盾的需求。你只是把审查的难度从"审代码实现是否正确"换成了"审需求描述是否完整"，并没有真正降低难度。

更麻烦的是，你还要审 AI 对 spec 的遵循程度——spec 说了要做 A，代码做没做？spec 说了不做 B，代码里有没有偷偷塞进来？这相当于多了一层审查工作。

所以 SDD 的真实 overhead 不只是"写 spec 的时间"，还包括"审 spec 的时间"和"验证代码与 spec 一致性的时间"。这三者加起来，可能比你直接 vibe coding + 审代码的总时间还要多。当然，如果 spec 质量很高且需求稳定，SDD 的总成本会更低。但如果需求频繁变动，这个算式就不一定成立了。

## 我的方案：六阶段 SDD Skill

综合了上面这些实践和教训，我给 Claude Code 写了一个 SDD 的 skill，流程是六个阶段：

```
1. Spec      → 定义"做什么"
2. Plan      → 定义"怎么做"
3. Tasks     → 拆分成原子任务
4. Implement → TDD：RED → GREEN → REFACTOR
5. Verify    → 收集验证证据
6. Review    → 两阶段审查
```

具体来说：

**Phase 1: Spec** — 写一个 Markdown，包含 Problem、Requirements（编号的功能需求）、Acceptance Criteria（可验证的验收标准）、Edge Cases（具体的边界行为，不能写"优雅处理"这种废话）、Out of Scope（明确不做的事情）。借鉴了 Spec-kit 的 constitution + specify 两个阶段，但合并成一个文档，减少冗余。

**Phase 2: Plan** — 技术方案、架构决策（选了什么、为什么选、放弃了什么）、需求到任务的映射、测试策略。借鉴了 Amazon Kiro 的 Design 文档理念。

**Phase 3: Tasks** — 把计划拆成原子任务，每个任务有关联需求、复杂度估算（S/M/L）、TDD 步骤。借鉴了 Spec-kit 的 tasks 阶段。

**Phase 4: Implement** — 严格 TDD。每个任务必须走完 RED → GREEN → REFACTOR。绝不跳过 RED。借鉴了 Ivo Kund 的 /implement 命令强制更新 spec 的思路。

**Phase 5: Verify** — 跑测试、lint、类型检查，记录输出，逐条对照验收标准。核心原则：没有新鲜的验证证据，就不能声称完成。

**Phase 6: Review** — 两阶段审查。Stage 1 查规格合规（每个 REQ 实现了吗？每个 AC 通过了吗？），Stage 2 查代码质量。Stage 1 不通过就不进入 Stage 2。借鉴了 Faros AI 的 "spec review gates" 理念。

这个 skill 的格式是 Claude Code 原生支持的 SKILL.md——YAML frontmatter 加 Markdown body。放在 `~/.claude/skills/sdd/` 目录下，Claude Code 启动时会自动加载。关键是 `description` 字段作为触发条件，当你的需求匹配到描述时就会自动走这个流程。

## 实测：让 Claude Code 跑一遍

纸上谈兵没用。我建了一个 TypeScript + Vitest 的计算器项目，已有 add 和 subtract 两个函数，任务是加一个 multiply 函数。

**Phase 1：** Claude Code 生成了 feat-multiply.md，包含 5 个功能需求、1 个非功能需求、6 个验收标准、5 个边界情况。结构完整，没有遗漏。

**Phase 2-3：** 生成了 3 个 Task，每个都有 TDD 步骤、验证命令、依赖关系。还包含了架构决策表（比如为什么放在同一个文件而不是单独模块）。

**Phase 4：** 严格执行了 RED → GREEN → REFACTOR。先写 3 个测试，确认失败，再写实现，全部通过，然后加边缘测试。最终 9 个测试全部通过。

**Phase 5：** 收集了完整的验证证据——测试输出（9 passed, 0 failed）、lint（ok）、类型检查（0 errors），每个 AC 和 EC 都映射到了具体的测试。

**Phase 6：** Stage 1（规格合规）PASS，Stage 2（代码质量）PASS。所有检查项逐条通过。

整个流程跑了大约 7 分钟。一个简单的 `a * b` 函数，Claude Code 产出了 4 份文档 + 9 个测试 + 完整的验证证据。

### 说几句实话

测试结果看起来很漂亮，但说实话有几个地方让我犹豫。

第一，这个测试场景太简单了。一个乘法函数，需求完全明确、边界情况可枚举、不存在需求变更——这恰好是 SDD 最适合的场景。如果换成"实现一个带权限管理的文件上传模块"这种需求本身就不清晰的任务，SDD 的前置阶段会不会变成一场漫长的拉锯？我没有测，但我怀疑会。

第二，Phase 2（Plan）和 Phase 3（Tasks）产出的内容有大量重复。Plan 里写了实现步骤，Tasks 里又把同样的步骤拆了一遍。如果是我自己用，我可能会合并这两个阶段，至少对小功能来说没必要拆这么细。Martin Fowler 说 Spec-kit 生成了冗余的 markdown——我怀疑我的 skill 在这方面也好不到哪去。

第三，整个流程的 7 分钟里，Claude Code 在写文档上花了大部分时间，真正写代码和测试的时间可能只有一两分钟。如果你只是想快速实现一个功能，这个 ratio 会让你觉得"太啰嗦了"。当然，这些文档的价值在需求变更或代码审查时会体现出来——但前提是你的项目真的会经历这些场景。

## 什么时候该用什么？

回到前面说的核心矛盾：**意图精确度和开发速度之间的 trade-off。** 与其搞一个"该用不该用"的二元判断，不如用两个维度来定位：

**维度一：需求明确度** — 你对要做什么有多确定？
**维度二：变更复杂度** — 这个改动涉及多少文件、多少模块？

{{< mermaid >}}
graph LR
    A[需求明确] --> B{变更复杂度}
    B -->|高| C[SDD 最佳场景]
    B -->|低| D[轻量 SDD]
    
    E[需求不明确] --> F{变更复杂度}
    F -->|高| G[混合模式]
    F -->|低| H[直接 vibe coding]
    
    C --> C1[Spec-First]
    C --> C2[Spec-Anchored]
    D --> D1[轻量 spec]
    G --> G1[先 vibe 再 SDD]
    H --> H1[直接 vibe]
{{< /mermaid >}}

**右上角（需求明确 + 高复杂度）：** SDD 的最佳场景。需求已经想清楚了，变更又涉及多个模块，写 spec 的投资回报率最高。用 Spec-First 或 Spec-Anchored。

**右下角（需求明确 + 低复杂度）：** 轻量 SDD 就够了。花 2 分钟写个 5-10 行的 spec，明确边界和验收标准，然后直接让 AI 写代码。不需要走完六个阶段。

**左上角（需求不明确 + 高复杂度）：** 最棘手的场景。建议用混合模式——先用 vibe coding 快速出一个原型，跑起来看看效果，确认需求之后再回过头来写 spec、规范化。Ivo Kund 的实验其实也暗示了这一点：他的 spec 不是一开始就完美的，是经过多轮迭代才达到"可以从 spec 重建代码"的质量。

**左下角（需求不明确 + 低复杂度）：** 直接 vibe coding。改动小，试错成本低，写 spec 反而浪费时间。如果 AI 写得不对，扔掉重写就行了。

当然，这个框架是理想化的。现实中的项目不会 neatly 落在四个格子里。但至少它能帮你做一个比"30 秒规则"更合理的判断。

## 写在最后

SDD 不是什么革命性的新方法论。它更像是一种"常识的结构化"——我们本来就应该先想清楚再动手，只是 AI 时代让这个"想清楚"变得更容易了（让 AI 帮你写 spec），也让"不想清楚就动手"的代价变得更大了（AI 会用光你的 token，写一堆方向错误的代码）。

但"想清楚"本身是有成本的，而且这个成本不总是能收回来。SDD 和 vibe coding 不是非此即彼的关系，它们是同一条光谱上的不同位置。聪明的做法是根据具体场景选择位置，而不是皈依某个方法论然后一刀切。

Fowler 警惕的"虚假控制感"是真实存在的——spec 写得再好，AI 也不一定 100% 遵循。但有了 spec，至少你有一个可以对照的基准，而不是在 AI 生成的代码迷宫里靠猜。有时候，一个不完美的基准也比没有基准强。
